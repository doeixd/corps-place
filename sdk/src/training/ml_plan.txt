Below is a robust, production-minded implementation plan for an ML system in TypeScript / Node, using TensorFlow.js (tfjs-node) with a small embedding + MLP model (plus strong anti-leakage + anti-memorization practices). This is the best fit if you want to stay all-in on TS/Node and still “actually learn correlations” from your tabular + categorical data.

Why this is the best TS/Node choice

Your problem is tabular + categorical IDs (corps, judges, captions, season) + numeric state features (trend, days since, gaps).

In JS/TS, the strongest practical option is:

Embeddings for high-cardinality categories

Numeric features for season state

Small MLP with heavy regularization

This generalizes well and won’t require giant models.

6) Model architecture (TF.js, robust)
6.1 The model: embeddings + pooled judges + MLP

Inputs:

Embeddings:

corps embedding 8–16 dims

Concatenate:
[numeric, corpsEmb, seasonEmb, divisionEmb, pooledJudgeEmb]

MLP:

Dense(128) + ReLU + Dropout(0.2) + L2

Dense(64) + ReLU + Dropout(0.2) + L2

Output head:

total score (1)

Loss:

Huber loss (more robust than MSE to outliers)

weight = exp(-lambda * ageInYears)

## Data + leakage guardrails

* **Hard “as-of” enforcement everywhere.** Every feature query should take `asOfTime` and filter `competition_date < asOfTime`. No exceptions.
* **Don’t use “daysTillFinals” unless you’re sure it’s not derived from future schedule quirks** (usually safe, but verify).
* **Rankings snapshots can leak** if they’re computed after the show you’re predicting. Only use snapshots strictly before the target show time.
* **Be careful with “eventName” / “slug”**: never feed raw strings. They’re identifiers and encourage memorization. Only derived features (region, month, indoor/outdoor, etc.).

## Normalize the world (you’ll thank yourself)

* **Canonical corps keys**: stable mapping for name variants (“Blue Devils” vs “Blue Devils B” vs sponsorship suffixes).
* **Canonical judge identities**: names change/spellings vary. Build a `judge_id` system with aliases + manual overrides.
* **Caption taxonomy**: captions/subcaptions change over time. Maintain a mapping table and a “missing caption” flag.

## Missing/partial data strategy

* For every nullable feature: include a **`has_*` flag**.
* Use safe defaults:

  * `0` for standardized numeric values after normalization (because mean≈0)
  * `UNK=0` for categorical IDs
* Early season: explicitly include **`showCountSoFar`** and **`hasLastShow`** so the model learns the “early season uncertainty” regime.

## Evaluation that matches your product

* Do **time-based splits only** (you already plan this).
* Add **bucketed metrics**:

  * MAE by `% through season` deciles
  * MAE by “days since last show”
  * MAE by “has panel” vs not
* Measure **rank accuracy** (derived): how often you correctly order top N for the event.
* Build a simple baseline and keep it forever:

  * `pred = lastScore + avgDailyGain(pctThroughSeason, corpsTier)`
  * If your model can’t beat it, something’s wrong (often leakage or feature bugs).

## Regularization / anti-memorization (practical knobs)

* Keep the model small (you did).
* Use **L2 on embeddings** and **dropout** in dense layers (you did).
* Consider **embedding dropout** (randomly zero out corps/judge embeddings sometimes) so it can’t rely on IDs alone.
* Consider **feature dropout**: randomly drop some numeric features during training to improve robustness to missing data.
* If you include judges: prefer **judge priors** (bias/spread) as numeric features first. Judge-ID embeddings are powerful but easier to overfit.

## Calibration + uncertainty

* Quantiles are great — but add a check:

  * enforce monotonicity at inference: if `p10 > p50`, swap/clamp; same for `p50 > p90`.
* Track calibration: % of true scores inside [p10, p90] should be ~80%. If it’s 50%, you’re overconfident.

## Data drift + rule changes

DCI scoring regimes shift subtly. Protect against it:

* Use **recency sample weights** (you have the hook).
* Track metrics by season; if the newest season degrades, retrain more frequently or increase recency weighting.

## Feature store versioning and reproducibility

* Save:

  * `feature_version`
  * ordered feature list (names in order) next to `numeric_norm.json`
  * the SQL hash (you did)
  * id map versions / vocab sizes
* Build a command to **rebuild datasets from scratch** (raw → normalized → features → train rows). This makes debugging possible.

## Operational reliability

* Add “data quality gates” before training:

  * % rows missing key features < threshold
  * no NaNs/infs
  * reasonable ranges (scores 0–100, pctThrough 0–100, etc.)
* Add “deployment gates”:

  * new model must beat previous on validation by at least epsilon (or not worse beyond tolerance)
  * otherwise keep current model

## Product/UX considerations that influence ML

* Users care about **relative** predictions more than exact points early season.

  * Consider outputting **rank probabilities** later (derived via sampling from quantiles).
* Explainability helps adoption:

  * even simple: “Based on last show + trend + rest days”
  * You can implement feature contribution approximations later (permutation importance offline).

## The biggest gotcha: lineup/attendance

If you’re “predicting event results,” you need to know **who is attending**.

* If lineup is unknown: your model can still predict each corps’ next score, but event rankings become guessy.
* If you can scrape/predict attendance: add lineup strength features and your event-ranking predictions get much better.

5) How to compute the features from your relational SQLite (queries)

I’ll assume you have these (or similar) tables after ingest:

competitions(slug, season, competition_date, day_of_season, percentage_through_season, latitude, longitude, ...)

corps_competition_results(competition_slug, division_name, corps_key, corps_total_score, ...)

judge_scores(competition_slug, division_name, judge_name, ...)

A. Corps count in class (competition/division)
SELECT COUNT(*) AS n
FROM corps_competition_results
WHERE competition_slug = ?
  AND division_name = ?;

B. Prior shows for that corps (same season, before target date)
SELECT c.competition_date AS date, r.corps_total_score AS total, c.latitude AS lat, c.longitude AS lon
FROM corps_competition_results r
JOIN competitions c ON c.slug = r.competition_slug
WHERE c.season = ?
  AND r.division_name = ?
  AND r.corps_key = ?
  AND c.competition_date < ?
ORDER BY c.competition_date DESC
LIMIT 3;


From this one query you can compute:

hasLastShow (>=1 row)

hasLast3 (==3 rows)

lastScoreTotal (row[0].total)

avgLast3Total (mean of 3 totals)

slopeLast3Total (based on totals in chronological order)

daysSinceLastShow (date diff between target date and row[0].date)

distanceKmFromLastShow (if lat/lon present in row[0] and target)

C. Best-so-far overall ranking as-of (division-wide)

Compute best score so far for all corps in the division (prior to target date):

SELECT r.corps_key, MAX(r.corps_total_score) AS best_total
FROM corps_competition_results r
JOIN competitions c ON c.slug = r.competition_slug
WHERE c.season = ?
  AND r.division_name = ?
  AND c.competition_date < ?
GROUP BY r.corps_key;


Then in TS:

sort descending by best_total

assign rank (1..N)

find leader best_total

for current corps:

overallRankAsOf = rank

gapToLeaderOverall = leader - corps_best

Set hasOverallRank=1 only if the corps appears in that map.

D. Weather
SELECT temperature_f, humidity_pct, wind_speed_mps, precipitation_mm
FROM competition_weather
WHERE competition_slug = ?;

E. Judge info (just the flag, if you’re not embedding yet)
SELECT 1
FROM judge_scores
WHERE competition_slug = ?
  AND division_name = ?
LIMIT 1;
