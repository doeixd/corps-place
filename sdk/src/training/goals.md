# DCI Score Prediction System (Effect SDK + SQLite + TFJS)

## Requirements, Expectations, and Goals — v1.0

### Purpose

Build a robust, production-ready score prediction system for Drum Corps International competitions that:

* Predicts **upcoming show outcomes** (per-corps total score distributions and derived rankings).
* Uses **season-to-date context** (results prior to the predicted event) without leaking future data.
* Handles **missing/partial inputs** (unknown judges, missing weather/coords, incomplete lineups).
* Stays **continuously updatable** as new recaps arrive via the Effect-based Corps Place SDK and its relational SQLite ingest.
* Is designed to **generalize** (learn correlations) rather than memorize.

---

## 1) High-Level Goals

### G1. Accurate, stable predictions

* Predict total score for each corps at an upcoming competition.
* Output uncertainty: **p10/p50/p90** (or equivalent quantiles).
* Provide derived ranking for the event lineup (sorted by p50).

### G2. Leakage-safe “as-of” modeling

* Every prediction and training example must only use information that would have been known **before** the target event date/time.

### G3. Operational robustness

* The system must run as reliable ETL + training + inference jobs with:

  * deterministic reproducibility
  * structured logging/metrics
  * safe retry/backoff where appropriate
  * bounded memory usage (streaming/batching)

### G4. Clean integration with the Effect SDK and relational SQLite

* Prefer the relational DB as source of truth for:

  * recaps, competitions, judge scores, corps results
  * feature computation inputs
* Use Effect services/layers to make jobs composable and testable.

### G5. Extensibility

* Ability to add new features, new targets (caption totals), and new model variants without breaking compatibility.
* Ability to re-run ETL and training across seasons from scratch.

---

## 2) Non-Goals (v1)

* Not attempting a “large transformer that ingests raw recap JSON” in v1.
* Not guaranteeing perfect predictions for rare edge cases (exhibition, unusual judging, weather anomalies).
* Not building an automated betting or wagering system.
* Not guaranteeing interpretability beyond basic feature importance proxies (optional later).

---

## 3) Users & Use Cases

### U1. Site visitor

* Views predicted scores/rankings for upcoming events.
* Sees confidence bounds and “what changed” since last update.

### U2. Admin/operator (you)

* Runs pipelines to sync data, rebuild ML rows, train model, evaluate model.
* Audits drift and model performance across season stages.

### U3. Bot/automation

* Posts predicted outcomes in Discord/Slack with short summaries.
* Refreshes after new recaps.

## 4) Data & System Components

### 4.1 Source data

**From Corps Place SDK (DCI API wrapper)**

* Seasons
* Competitions/events
* Recap payloads (scores by corps/caption/subcaption)
* Judge assignments (via recap/judge score records)
* Optional: performances/ordering if available

### 4.2 Primary storage

**Relational SQLite/LibSQL DB** generated by the SDK ingest (authoritative dataset).

### 4.3 Derived ML storage

In the same DB (recommended) or separate DB:

* `ml_training_rows` (materialized feature rows)
* vocab tables: `ml_corps_vocab`, `ml_judge_vocab`, `ml_division_vocab`, `ml_season_vocab`
* `ml_model_runs` (model metadata + evaluation metrics)

### 4.4 Model artifacts

File-based directory per run:

* `model.json` + weights
* `numeric_norm.json` (mean/std)
* `features.json` (exact feature order + defaults + missing rules)
* `meta.json` (run id, git commit, data hash, spec hash, training window)
* optional: calibration metrics, quantile residual summaries

## 5) Feature Spec Contract (Hard Requirement)

### R5.1 Stable feature vector schema

* The **numeric feature vector order** and defaults are defined by `features.json`.
* Training, evaluation, and inference must use the **same** `features.json` version.

### R5.2 Missing-value handling

* If a feature has `missingFlag`, inference must:

  * set the flag to **1** when the value is present
  * set it to **0** when missing
  * use `defaultValue` when missing
* All other features without a missingFlag must still fall back to `defaultValue`.

### R5.3 Current feature set (v1.1)

Numeric fields and flags as provided:

* percentageThroughSeason, dayOfSeason, showOfSeason, performanceOrderInClass, corpsCountInClass
* daysSinceLastShow, lastScoreTotal, avgLast3Total, slopeLast3Total
* overallRankAsOf, gapToLeaderOverall
* distanceKmFromLastShow
* temperatureF, humidityPct, windSpeedMps, precipitationMm
* hasLastShow, hasLast3, hasOverallRank, hasWeather, hasJudgeInfo

## 6) Leakage Safety Requirements (Critical)

### R6.1 As-of constraint

For a training row targeting `(season, competition_slug, corps_key, division)`:

* Any derived feature using “prior results” must only consider competitions where:

  * `competition_date < target_competition_date`

### R6.2 Ranking-as-of constraint

`overallRankAsOf` and `gapToLeaderOverall` must be computed only from data prior to the target event.

### R6.3 No target-derived proxy features

Do not use:

* final rank at the target competition
* any score at the target competition (except as the label `y_total`)
* anything computed using target scores (even indirectly)

### R6.4 Time-based splits

Validation/test splits must be time-based (by season and/or by date), never random row splitting, to prevent leakage across near-identical distributions.

---

## 7) Training & Modeling Requirements

### R7.1 Output type

* The model must output at least one central tendency value (`p50` or mean).
* Preferred: quantile outputs `p10`, `p50`, `p90` for uncertainty.

### R7.2 Generalization controls (anti-memorization)

Must include:

* Weight decay (L2)
* Dropout in dense layers
* **Embedding dropout / feature dropout** (as you listed)
* Early stopping based on validation loss
* Minimum baseline comparison (see evaluation)

### R7.3 Handling partial inputs

* Inference must accept missing:

  * weather
  * last show history
  * judge info
  * coordinates
* Missing must not throw; it must be encoded through defaults + flags.

### R7.4 Model choice constraints (v1)

* Use a small-to-medium MLP + (optional) embeddings for categorical inputs.
* Avoid large transformers in v1.
* Sequence modeling can be a v2 milestone.

### R7.5 Re-training strategy

* Predictions recomputed whenever new recaps arrive (cheap).
* Retraining cadence:

  * during season: nightly or on-demand
  * off-season: monthly or manual
* Retraining should be gated by evaluation thresholds.

---

## 8) Evaluation Requirements (Must Have)

### R8.1 Metrics

At minimum:

* MAE for total score (overall)
* MAE bucketed by `percentageThroughSeason` (or `dayOfSeason` bins)
* Top-3 accuracy for event lineup ranking (derived from p50)

### R8.2 Baselines

Compare against:

* Baseline A: lastScoreTotal (if available else 0)
* Baseline B: avgLast3Total (if available else lastScoreTotal)
* Baseline C: “rank-as-of / best-so-far” derived prediction (optional)

Model must beat baselines on validation before being considered “deployable”.

### R8.3 Reporting

Evaluation script must emit:

* JSON metrics artifact saved with the run
* Human-readable summary log
* Optional per-corps error breakdown (top offenders)

---

## 9) ETL Requirements (Build ML Rows)

### R9.1 Deterministic, idempotent ML row generation

* Running `BuildMlRows` multiple times yields the same rows for the same underlying relational data.
* Use upsert semantics on unique keys.

### R9.2 Performance

* Must stream competitions; avoid loading entire DB into memory.
* Must batch or reuse shared computations per competition/division:

  * corpsCountInClass
  * weather lookup
  * overall best-so-far ranking map (precompute once per competition/division)

### R9.3 Data completeness expectations

* Some seasons will have missing:

  * weather
  * coordinates
  * judge panel data
  * performance ordering
* System must degrade gracefully.

### R9.4 Auditability

Every row should be reproducible from:

* competition slug
* corps key
* season/date
* feature spec version

---

## 10) Inference Requirements (Production)

### R10.1 API contract

Given a target competition (upcoming or historical “as-of”):

* Build per-corps feature vectors
* Return:

  * p10/p50/p90 per corps
  * derived ranking (sorted by p50)
  * metadata: model version, timestamp, feature spec version, missing-data flags summary

### R10.2 Latency

* Single event lineup prediction should complete fast enough for web usage.
* Model should be loaded once and reused (avoid loading weights per request).

### R10.3 Determinism

* For the same model artifacts + same inputs, outputs must be deterministic (set TFJS seed where possible; avoid nondeterministic GPU ops if relevant).

## 11) Observability & Ops Requirements

### R11.1 Effect observability integration

All jobs should emit structured telemetry:

### R11.2 Versioning and provenance

### R11.3 Failure handling

* ETL and sync jobs must be retryable.
* Training failures must not overwrite the “current” deployed model.

## 14) Success Criteria

### S1. Correctness

* No leakage: verified by tests that ensure “prior-only” queries.
* Stable feature ordering: verified by hashing `features.json` and refusing mismatch.

### S2. Performance

* ETL completes for ~10 seasons within acceptable time on a dev machine (streaming, not quadratic).
* Inference for one event lineup completes quickly and reliably.

### S3. Predictive value

* Model beats baselines on validation and test.
* MAE improves as `percentageThroughSeason` increases (expected behavior).
* Top-3 accuracy is meaningfully above naive baselines.

## 15) Explicit Expectations (What to assume is true)

* You have ~10 seasons of recap data (enough for v1 MLP).
* Not all features will be present for all rows; flags must capture this.
* Judge panels vary by event and may be missing for future events.
* Weather and coordinates may start incomplete and be added later.
* Performance order may be unavailable initially; default to 0 until you ingest it.
