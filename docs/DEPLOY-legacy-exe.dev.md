# Deploy — corps.place (LEGACY / never deployed)

> ⚠️ **Superseded — historical only.** This describes an **exe.dev + systemd + nightly-cron**
> plan that was **never deployed**. Production actually runs on **Coolify + Docker** — see
> [`DEPLOYMENT_REALITY.md`](./DEPLOYMENT_REALITY.md) (source of truth) and
> [`INFRASTRUCTURE.md`](./INFRASTRUCTURE.md). The serving image has no tfjs/model/relational
> DB and there is no on-box cron; data is built offline and pushed to Turso. Only the
> *architecture rationale* below (predictions/read-model are precomputed; serving needs no
> GPU/model) still holds — the hosting mechanics do not. Kept for reference; do not follow it.

Production deployment notes, the reasoning behind them, and a step-by-step runbook.

**TL;DR:** one **monolith VM** (exe.dev, 2 vCPU / 8 GB / persistent disk). The web
serves SSR + cached reads; a **nightly cron** scrapes new data, (optionally)
fine-tunes the model, and **pre-generates predictions** into the local SQLite DB.
No Cloudflare required (exe.dev's edge does TLS); add it later only for image/asset
caching.

---

## 1. Architecture (what runs where)

```
exe.dev VM (Ubuntu/exeuntu, KVM, persistent disk)
├─ web        node .output/server/index.mjs        (always-on, systemd)   ← SSR + DB reads
├─ DB         sdk/dci-relational.db  (2.4 GB+)      (on the VM's disk)     ← read by web, written by cron
├─ models     sdk/models/v9_subcaption_fixed/<run>  (latest in prod)
└─ nightly    npx tsx scripts/seasonUpdateWorkflow  (cron/systemd timer)   ← scrape→ingest→[fine-tune]→predict
```

- **exe.dev edge** terminates TLS, gives `vmname.exe.xyz` (or your domain), forwards
  to the web port. HTTP/2, HSTS, WebSockets/SSE all handled — no nginx/certbot.
- **Everything is one VM** because each exe.dev VM has its **own disk**; a separate
  worker VM couldn't see this VM's DB. The web and the nightly job share the DB by
  living on the same box.

## 2. Why this shape

The workloads have very different profiles; only one is heavy:

| Work                              | When                  | Cost                           | On request path?               |
| --------------------------------- | --------------------- | ------------------------------ | ------------------------------ |
| Web SSR + DB reads                | every request         | tiny                           | yes                            |
| Inference (generate a prediction) | per event             | ~seconds CPU                   | **no — pre-generated by cron** |
| Scrape + ingest                   | nightly               | minutes, I/O                   | no                             |
| **Fine-tune**                     | nightly (after shows) | **~20–45 min, ~5 GB RAM, CPU** | no                             |

Key decisions:

- **Predictions are cached DB rows.** The web only ever **reads** them. All heavy
  work (scrape/ingest/train/predict) runs in the nightly job and writes the DB.
  → the serving process needs no GPU and barely any RAM.
- **Monolith is fine** because the one downside (training contending with serving)
  is moot at 3 a.m. when traffic is ~0.
- **No Cloudflare Workers / wasm / ONNX / on-device.** tfjs-node is native (can't run
  on Workers), training can't run on Workers at all, and the 2.4 GB DB is the gravity
  of the system. Edge inference solves a problem we don't have.

### Measured (so the sizing isn't a guess)

- **Inference:** ~seconds, ~1 GB.
- **Fine-tune (`trainModelV9Subcaption-fixed`, loading latest prod model):** a short
  3-epoch × 512-sample run took **85.6 s and peaked ~4.8 GB RSS**. Peak RAM is roughly
  **fixed** (full feature-set load + tfjs + the many eval slices), independent of epoch
  count; wall-time scales with `epochs × samples` on ~30–40 s of fixed load/eval/save.
  A full nightly fine-tune (default 30 epochs, `patience 10` early-stop) ≈ **10–30 min
  on 4 vCPU, ~20–45 min on 2 vCPU**.

## 3. Sizing

The **fine-tune peak (~5 GB)** is the binding constraint.

- **Retrain nightly (default plan): 8 GB RAM minimum** (4 GB OOMs), 2–4 vCPU, NVMe/SSD,
  ~40 GB+ disk. exe.dev Personal (2 vCPU / 8 GB / 100 GB) fits, with the 2-vCPU caveat
  that the nightly run leans toward ~45 min (fine overnight).
- **Inference-only v1 (retrain manually/occasionally elsewhere):** 2 vCPU / 4 GB is
  enough; the 8 GB is _entirely_ the cost of automatic retraining.

> The ~5 GB peak is inherent to the current trainer (it loads everything + evaluates a
> dozen slices). If 8 GB ever feels tight, trimming the nightly eval slices cuts peak RAM.

## 4. exe.dev specifics

- Real KVM VM, key-only SSH (brokered through exe.dev), **only 443 exposed** via the edge.
- **Pooled plan:** $20 Personal = 50 VMs / 100 GB pooled disk / shared CPU+RAM pool.
  Dedicate the pool to the one prod VM — don't run other heavy VMs alongside it during
  the nightly train. (Extra VMs are great for staging/throwaway, not for this DB-coupled
  workload, since disks aren't shared.)
- **`exeuntu`** image tracks Ubuntu → glibc, so tfjs-node prebuilt binaries work.
- Private-by-default proxy: run `share set-public <vm>` to make the site public.
- TLS, custom domain, WebSockets/SSE handled at the edge.

## 5. Before you deploy — decisions

1. **Nightly retrain, or inference-only v1?** (Drives whether you need the 8 GB and the
   `--fine-tune` flag below.) Recommended: ship inference-only first, enable `--fine-tune`
   once it's stable.
2. **Domain:** use `vmname.exe.xyz` or point your own domain at the exe.dev edge.
3. **Backups:** decide where nightly DB dumps go (see §10). **Do this on day one** — more
   so on a newer provider.

## 6. One-time setup (runbook)

SSH in (`ssh exe.dev new corps-prod --image exeuntu` then `ssh exe.dev ssh corps-prod`,
per their CLI), then:

```bash
# 1. Node 20 (tfjs-node pins to Node 20; the web is happy on it too)
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo bash -
sudo apt-get install -y nodejs build-essential git

# 2. Swap — OOM insurance for the nightly training spike
sudo fallocate -l 4G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

# 3. Code
sudo mkdir -p /srv && cd /srv
git clone <your repo> corps-place && cd corps-place
npm ci
(cd sdk && npm ci)               # tfjs-node, tsx, @libsql/client, etc.

# 4. Data: place the 2.4 GB DB + the latest model on the VM disk
#    (rsync/scp from your machine — do NOT bake the DB into git/images)
#    -> sdk/dci-relational.db, sdk/dci-relational.db-wal/-shm
#    -> sdk/models/v9_subcaption_fixed/<latest-run>/

# 5. Build the web
npm run build                    # vite build -> .output/server/index.mjs
```

## 7. Web service (always-on)

`/etc/systemd/system/corps-web.service`:

```ini
[Unit]
Description=corps.place web
After=network.target

[Service]
WorkingDirectory=/srv/corps-place
Environment=NODE_ENV=production
Environment=PORT=3000
EnvironmentFile=/srv/corps-place/.env
ExecStart=/usr/bin/node .output/server/index.mjs
Restart=always
RestartSec=2

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl enable --now corps-web
# expose port 3000 to the exe.dev edge:
ssh exe.dev share port corps-prod 3000
ssh exe.dev share set-public corps-prod      # when ready to go public
```

The web reads `sdk/dci-relational.db` directly (fast, local). `start` script
(`node .output/server/index.mjs`) is the same thing if you prefer `npm start`.

## 8. Nightly job (scrape → ingest → [fine-tune] → pre-generate)

`/srv/corps-place/scripts/nightly.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail
cd /srv/corps-place/sdk
# inference-only: drop --fine-tune. Full retrain: keep it.
nice -n 10 npx --yes tsx scripts/seasonUpdateWorkflow.ts \
  --season 2026 \
  --fine-tune --model-dir latest \
  >> /var/log/corps-nightly.log 2>&1
```

The workflow already chains: event/website ingest → **corps scrape** (`scrapeCorps`,
skip with `--skip-corps`) → lineup/venue backfills → website recaps → ML rebuild →
fine-tune → and you regenerate predictions for upcoming events. `nice` keeps even an
overlapping daytime run from starving the web.

Schedule it after scores release (run nightly; it's cheap when there's nothing new):

```cron
# /etc/cron.d/corps-nightly  — 03:15 daily
15 3 * * *  root  /srv/corps-place/scripts/nightly.sh
```

(or a `systemd` timer if you prefer). Set `BROWSERBASE_API_KEY` in `.env` so the
scrape step bypasses Cloudflare.

## 9. Code change for prod: predictions read-only / pre-generated

Today the web spawns `npx tsx` to generate a prediction on cache-miss
(`app/lib/event-prediction-api.ts` `getOrCreate…`). In prod the **nightly job should
pre-generate** predictions for upcoming events so the web never spawns tfjs on the
request path (faster, no native deps needed in the serving process, and it sidesteps the
spawn races we already fixed once). Keep the on-demand path as a dev fallback. **(Action
item — not yet done.)**

## 10. Data: backups & growth

- **Backups (do this):** nightly `sqlite3 sdk/dci-relational.db ".backup '/tmp/db.bak'"`
  (or copy the file while the WAL is checkpointed) and push to object storage (R2/S3).
  The DB is the source of truth — losing it loses all scrapes + cached predictions.
- **Growth:** the scrape archive (`corps_page_scrapes`, `event_page_scrapes`,
  `website_recaps`) keeps full history (time travel), and each nightly fine-tune saves a
  new model dir. Over a season that's GBs. 100 GB is roomy, but periodically **prune old
  scrape rows** (keep latest + N) and **keep only the latest model dir** in prod (archive
  older runs off-box).

## 11. Environment (`.env` on the VM)

```bash
NODE_ENV=production
PORT=3000
BROWSERBASE_API_KEY=...            # scraping (Cloudflare bypass)
# DCI_RELATIONAL_DB_URL=file:./sdk/dci-relational.db   # default is fine if cwd is repo root
# DCI_API_SOURCES=db,website                            # default; network API is dead

# Read-model fast path (READ_MODEL_PLAN). When set, page reads come from the
# tiny precomputed read-model.db via indexed lookups instead of running CTEs
# over the 3.4 GB relational DB — this is the "instant reads" win. Unset = falls
# back to the shared builders against the big DB (correct, just slower).
#
# NOTE: deploy.ps1 sets this automatically for the prod backend and emits a fresh
# read-model before warming it, so you don't normally set it here. Ingest's final
# step also re-emits, and the running server reconnects on the new file (mtime
# watch). Set it explicitly only if running `node .output/server` by hand.
READ_MODEL_DB_URL=file:./sdk/read-model.db
```

Read-model is also rebuilt by `cd sdk && npx tsx scripts/emitReadModel.ts`
(`--dry-run`, `--only`, `--json-snapshot <dir>`). `deploy.ps1`: `-Start` brings up
the last build with no rebuild/emit, `-SkipEmit` deploys without re-emitting,
`-Emit` forces an emit, `-Stop`/`-Status` as before.

## 12. Cloudflare (optional, not required)

exe.dev's edge already gives TLS + custom domain + streaming, so **skip CF for v1.** Add
it later **only** for CDN caching (your `proxiedImage` image proxy + hashed static assets
→ offloads the 2-vCPU box, saves egress) or WAF/DDoS. If you add it: domain on CF
(orange-cloud) → exe.dev edge as origin, **SSL Full (Strict)**, `share set-public`, and
**cache static + images only — never HTML/SSR/`/api/fate*`** (the pages are dynamic and
change nightly). Verify streaming SSR / Fate-live still stream through the double-proxy.

## 13. Gotchas checklist

- [ ] **Node 20** on the box (tfjs-node prebuilts); `exeuntu` = Ubuntu/glibc ✓ (avoid Alpine/musl).
- [ ] **NVMe/SSD** disk (SQLite random reads over 2.4 GB).
- [ ] **Swap** enabled (training spike OOM insurance).
- [ ] **DB on the persistent disk**, never baked into the image/git.
- [ ] **Backups** running to off-box storage from night one.
- [ ] `share set-public` only after you've verified the site.
- [ ] Pre-generate predictions (§9) before relying on the web for them.
- [ ] Don't run other heavy VMs sharing the 8 GB pool during the nightly train.

## 14. Updates / redeploys

```bash
cd /srv/corps-place && git pull && npm ci && (cd sdk && npm ci) && npm run build
sudo systemctl restart corps-web
```

The DB + models persist across redeploys (they're on the VM disk, outside the repo build).
