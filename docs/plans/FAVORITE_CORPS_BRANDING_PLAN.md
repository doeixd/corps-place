# Favorite Corps Branding Plan

Goal: make the user's favorite corps drive the site's accent color, Corps Place
logo palette, and browser favicon in a way that is deterministic, fast on first
paint, accessible, and easy to reason about.

This plan builds on `docs/plans/CORPS_COLORS_PLAN.md`. That plan establishes the
source color data (`color_primary`, `color_secondary`) and shared OKLCH palette
derivation. This plan covers the app-level favorite behavior that consumes those
colors.

## Current State

- A single favorite corps is stored in `localStorage` under
  `corps-place-favorite-corps`.
- `app/stores/favorite-corps-store.ts` persists the favorite and applies
  `--primary`, `--primary-foreground`, and sometimes `--logo-dark` to
  `document.documentElement`.
- `app/routes/__root.tsx` includes a small inline no-flash script that reads the
  persisted favorite before React mounts and applies the same root variables.
- `app/components/logo.tsx` renders the Corps Place SVG using CSS custom
  properties such as `--logo-accent`, `--logo-dark`, and `--logo-light`.
- `app/app.css` derives most logo colors from `--primary` via relative OKLCH and
  registers those color custom properties with `@property`, enabling smooth color
  interpolation in supporting browsers.
- The browser favicon is static: `<link rel="icon" href="/logo.svg">` points to
  `public/logo.svg`, whose fills are hard-coded. `/favicon.ico` returns `204`.

The current implementation is a good base for "tint the Corps Place brand by the
favorite corps." It is not a complete implementation of "replace the site logo
with the favorite corps' own logo."

## Product Decision

Recommended v1 behavior:

- The site keeps the Corps Place logo shape.
- Favoriting a corps recolors the Corps Place logo and primary accent using that
  corps' brand colors.
- The favorite corps' actual logo remains visible in corps cards, tables, and
  profile pages, but does not replace the main app identity.
- The favicon should match the same tinted Corps Place logo, not the favorite
  corps logo, unless we deliberately choose a heavier per-corps favicon feature.

Rationale: a stable app mark keeps navigation recognizable, while the favorite
still personalizes the UI. Swapping the nav/favicon to arbitrary corps logos
creates shape, contrast, transparency, and licensing edge cases.

## Invariants

1. Favoriting a corps never requires a network request to repaint the shell.
2. First paint uses the persisted favorite palette when available.
3. Switching favorites is deterministic and replaces the previous favorite.
4. Clearing the favorite restores the default app palette and favicon.
5. Theme changes use the light/dark derived palette for the same favorite.
6. Stored local data is treated as untrusted; corrupt favorites cannot set
   arbitrary CSS values.
7. The favicon, nav logo, and primary accent derive from the same sanitized
   favorite palette.
8. Browsers without `@property` or relative OKLCH still get a readable fallback,
   even if transitions are instant or less exact.

## Data Shape

Keep the persisted favorite compact, but make it versioned and validated:

```ts
type PersistedFavoriteV2 = {
  version: 2;
  corpsKey: string;
  name: string;
  slug: string | null;
  colorPrimary: string | null;
  colorSecondary: string | null;
  lightPrimary: string;
  lightPrimaryForeground: string;
  darkPrimary: string;
  darkPrimaryForeground: string;
  logoDark: string | null;
  faviconSvg: string;
  addedAt: string;
};
```

Notes:

- Preserve `addedAt` during hydration. The current `cleanFavorite()` recomputes
  it, which makes the field misleading.
- Recompute palette fields from stored hex during hydration, but retain the old
  `addedAt`.
- Store only CSS values generated by our own palette function, not user-supplied
  CSS strings.
- `faviconSvg` may be omitted if we decide to generate it in the no-flash script
  from palette fields instead. Storing the final data keeps the head script tiny.

## No-Flash Paint

The current head script is conceptually right: it runs before React hydration and
sets the theme and favorite palette on `<html>`.

Improvements:

1. Move the script body into a small source module that exports the string, so it
   can be unit-tested as plain logic or at least kept readable.
2. Add strict shape validation before applying values:
   - `version === 2`
   - palette fields are strings starting with `oklch(` or known fallback hex
   - `logoDark` is null or a generated `oklch(...)`
   - ignore the favorite if validation fails
3. On invalid stored favorite, remove the key from localStorage if possible.
4. Apply both root colors and favicon in the same script.
5. Avoid writing empty string for missing `--logo-dark`; remove the property
   instead once React owns the DOM. In the no-flash script, if removal is too
   verbose, skip setting it when absent.

The no-flash script should not import app code at runtime. It must remain inline
and self-contained in the HTML head.

## Switching Favorites

Switching favorite corps currently works by replacing the store's single
favorite. Keep that model.

Improvements:

- Add a single `applyFavoriteBranding(favorite, options?)` function used by:
  - favorite store subscription
  - theme store subscription
  - tests
  - future favicon update code
- Keep DOM writes ordered:
  1. compute active theme
  2. set `--primary`
  3. set `--primary-foreground`
  4. set/remove `--logo-dark`
  5. update favicon
- Clearing favorite should remove all favorite-owned overrides in one function.
- Keep switching animated for favorite changes, but not for light/dark theme
  toggles. Theme toggles already disable transitions globally, which is the
  right default.
- The favorite button itself should not animate on click. Its icon, border,
  background, and text color should snap immediately to the newly selected corps
  state. If the shell logo/accent animates, that animation must not make the
  button feel delayed or ambiguous.

## Hue Animation

The existing CSS transition is good:

```css
html {
  transition:
    --primary 0.2s ease-out,
    --primary-foreground 0.2s ease-out,
    --logo-accent 0.2s ease-out,
    --logo-accent-vivid 0.2s ease-out,
    --logo-accent-muted 0.2s ease-out,
    --logo-dark 0.2s ease-out,
    --logo-detail 0.2s ease-out,
    --logo-light 0.2s ease-out;
}
```

Keep the animation, with two refinements:

- Respect reduced motion. Under `prefers-reduced-motion: reduce`, either remove
  the transition or reduce it to near-instant.
- Do not animate the pressed favorite button. Button feedback should be instant;
  hue animation is for the surrounding shell/logo only.
- Test at least three hard hue transitions: red → blue, blue → green, and a
  low-chroma/monochrome fallback. Registered color interpolation can pass
  through muddy intermediate colors; if it looks bad, shorten the duration to
  100-140ms.

Do not animate by manually interpolating hue in React. CSS custom property
transitions are simpler and keep repaint local to style.

## Favicon

The favicon is currently incomplete for favorite branding.

Recommended v1:

- Generate a small SVG favicon from the same palette used by `Logo`.
- Use a lightweight icon variant rather than the full detailed 512x512 path if
  possible. The tab icon is tiny; over-detailed SVGs become noise.
- Update the existing `<link rel="icon">` href to a `data:image/svg+xml` URL on
  favorite/theme changes.
- Restore `/logo.svg` when the favorite is cleared.
- Keep `/favicon.ico` as a simple fallback route or serve a real static icon
  instead of `204`.

Implementation sketch:

```ts
function setFavicon(svgHref: string | null) {
  const selector = 'link[rel="icon"][data-app-icon="true"]';
  let link = document.querySelector<HTMLLinkElement>(selector);
  if (!link) {
    link = document.createElement('link');
    link.rel = 'icon';
    link.type = 'image/svg+xml';
    link.dataset.appIcon = 'true';
    document.head.appendChild(link);
  }
  link.href = svgHref ?? '/logo.svg';
}
```

Root document should mark the managed icon:

```tsx
<link rel="icon" href="/logo.svg" type="image/svg+xml" data-app-icon="true" />
```

No-flash favicon:

- If `faviconSvg` is stored, the inline script can set the icon link immediately.
- If not stored, the inline script should not duplicate complex SVG generation;
  accept a favicon flash or keep the default favicon until React runs.

Recommendation: store a pre-generated tiny favicon data URL in the favorite
payload. It keeps the no-flash script small.

## Logo Palette

Current logo palette derivation:

- `--logo-accent*`, `--logo-detail`, and `--logo-light` derive from `--primary`.
- `--logo-dark` can be overridden from the favorite corps secondary color.

This is good enough for v1, but the secondary-color behavior needs guardrails:

- If `colorSecondary` is missing or too close to primary, derive `--logo-dark`
  from primary instead of forcing a weak secondary.
- If secondary is very low chroma or very light, clamp it aggressively so it
  remains a structural dark fill.
- Consider deriving one additional logo detail color from secondary for corps
  with strong two-color marks, but do not overfit. The app logo should stay
  coherent.

Longer-term option:

```ts
type FavoriteLogoPalette = {
  accent: string;
  accentVivid: string;
  accentMuted: string;
  dark: string;
  detail: string;
  light: string;
};
```

Compute and persist all six logo variables instead of deriving most of them in
CSS. That makes no-flash behavior and favicon generation simpler, but increases
stored data. Only do this if CSS relative OKLCH support causes real browser
issues.

## Accessibility

- Keep `--primary-foreground` contrast-picked against `--primary`.
- Audit primary-colored buttons, badges, nav active states, and selection color
  for contrast in both themes.
- Avoid very saturated dark-mode accents that bloom against dark backgrounds.
- Favicon color does not have strict WCAG requirements, but should remain
  recognizable in light and dark browser chrome.

## Tests

Add focused tests around pure behavior first:

- `cleanFavorite()` accepts v1/v2 payloads and preserves `addedAt`.
- corrupt localStorage values are ignored.
- missing colors fall back to `FALLBACK_PRIMARY`.
- switching favorite A → B replaces all root variables.
- clearing removes favorite-owned variables.
- theme light/dark changes use the correct stored palette.
- favicon href updates on set/clear.

Where to test:

- Pure palette/data tests can live near `app/stores/favorite-corps-store.ts`.
- DOM behavior can use jsdom/Vitest if the app test setup supports it.
- Visual/manual checks: favorite three corps with distinct colors, reload in
  light and dark mode, verify no visible flash.

## Implementation Sequence

1. Extract favorite branding helpers:
   - `computeFavoriteBranding(input, previousAddedAt?)`
   - `cleanFavorite(raw)`
   - `applyFavoriteBranding(favorite)`
   - `clearFavoriteBranding()`
   - `setFavicon(href)`
2. Preserve `addedAt` during hydration and add a versioned persisted shape.
3. Harden the no-flash script with validation and managed favicon support.
4. Generate and store a tiny favorite-colored SVG favicon data URL.
5. Update `RootDocument` icon link with `data-app-icon="true"`.
6. Add reduced-motion handling for logo/accent variable transitions.
7. Add tests for data cleaning, DOM variable application, theme switching, and
   favicon updates.
8. Manually verify:
   - no favorite → default logo/accent/favicon
   - favorite A reload → no default-color flash
   - favorite A → favorite B → smooth color transition
   - clear favorite → default restored
   - light/dark toggle with favorite → no smear, correct palette

## Open Questions

- Should the favicon use the full Corps Place logo path or a simplified mark?
- Should the app ever show the favorite corps' actual logo in the nav, or is
  tinting the Corps Place logo the final product decision?
- Should the favorite be synced server-side for signed-in users, or remain
  device-local?
- Should the favorite influence only the shell (`--primary`) or also per-page
  chart defaults and card accents?

## Definition of Done

- Favorite corps tinting has one shared application path for React and no-flash.
- Stored favorites are versioned and validated.
- Switching, clearing, and theme toggling are deterministic.
- The favicon follows the favorite palette and resets correctly.
- Reduced-motion users do not get unnecessary color animations.
- Tests cover the data and DOM behavior.
- Manual reload checks show no visible default-brand flash.
