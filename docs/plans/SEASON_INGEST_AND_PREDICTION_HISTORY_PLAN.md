# Season Ingest & Prediction-History Plan

**Status:** proposal / not yet started — **key decisions finalized (see §0.1)**
**Author:** drafted with Claude, 2026-06-18
**Urgency:** the 2026 DCI season's first scored events are **June 26–27, 2026** (~8 days out). Verified live on 2026-06-18: `dci.org/scores/?season=2026` lists upcoming events but **zero recaps** — we cannot validate against real data yet, so correctness must be proven against a mocked DCI.
**Scope:** (1) make the score ingest path provably season-ready (watch the scores list, follow the link, ingest), (2) make full-season prediction recalcs **non-destructive** so we keep a versioned "prediction as of ___" history, (3) surface that history as a slider on the corps season chart, (4) cover all of it with robust integration tests against a mocked DCI.

---

## 0. TL;DR / decision

- **Don't predict slugs — watch the list and follow the link.** The score list page
  (`/scores/?season=2026`) is both the *watch target* and the *source of the exact
  recap URL*. `parseScoresListHtml` (`sdk/src/websiteRecap.ts:185`) already extracts the
  recap `href` from each row. Polling = diff the list against what we've ingested;
  a new row → follow its embedded recap link → scrape → ingest. DCI renames, sponsor
  suffixes, and prelims/finals naming stop mattering because we never construct the slug.
- **Slug-guessing demotes to a safety net.** Keep a candidate-probe fallback only for
  the rare malformed/missing-link row. It is off the critical path.
- **Prediction history is ~90% already supported by storage.** `model_event_prediction_runs`
  is keyed by `(event_slug, predicted_at)` and never hard-deletes; `INSERT OR REPLACE`
  only collides on identical `predicted_at`. What flattens history is the **read path**
  (`buildCorpsSeasonScores`, `readModel/builders/corps.ts:257`, does `MAX(predicted_at) GROUP BY event_slug`).
  We make recalc stamp a shared snapshot timestamp and make the read path snapshot-aware.
- **A season recalc = one snapshot, future events only.** Every event produced in a
  recalc shares one `generated_at`, so a snapshot ≡ all runs with the same `(season, predicted_at)`.
  Recalc writes runs **only for events not yet completed**. "Freeze the past" then falls out
  for free: rendering "as of date *d*" picks, per event, the run with the latest `predicted_at ≤ d`;
  completed events have no newer run and show actuals.
- **Polling is scheduled by event end time.** Read the scheduled end from DCI's event page;
  start densely watching the scores list when the show should be ending; back off once the
  row appears (or after a timeout with an alert).
- **Everything is tested against a fixture-backed mock DCI** — no network in tests.

### 0.1 Finalized decisions (from review)

| Decision | Choice |
|---|---|
| Snapshot identity | **Season-wide snapshot runs** — one shared `predicted_at`/label per recalc; slider stops are clean discrete dates. |
| Past events on recalc | **Freeze past, recalc future only** — past runs untouched; completed events get actuals filled in. |
| Polling trigger | **Scheduled by event end time** — when DCI's schedule says the event ends, start watching the scores list; poll until the score row appears, then back off. |
| Slug handling | **Watch-the-list / follow-the-link** in the happy path; slug-candidate probing kept only as a fallback. |

## 1. Background — how the system works today

### 1.1 Ingest path (works for 2013–2025; unproven for 2026)
- **Discovery:** `sdk/src/websiteApi.ts` fetches `/scores/?season=YYYY` and the
  `wp-admin/admin-ajax.php?action=score_events` AJAX endpoint, with an HTML fallback
  (`parseScoresListHtml`). Each list row already carries the recap `href`/slug.
- **Recap parse:** `parseRecapHtml` (`websiteRecap.ts:247`) → `WebsiteRecap`
  → `buildCorpsScoresFromWebsiteRecap` → `CorpsScore[]`.
- **Ingest:** `ingestWebsiteRecap` (`sdk/src/relational.ts:5738`) writes `competitions`,
  `corps_scores`, `category_scores`, `caption_scores`, `judges`, and the
  `event_to_competition` bridge.
- **Orchestration:** `sdk/scripts/scrapeWebsiteRecaps.ts`,
  `collectScoreListEntries` (dedupes by recap slug), `scrapeWebsiteRecapByEntry`.

### 1.2 Slug relationship (the wrinkle the user flagged)
- `events.slug` is **non-prefixed** (`dci-tour-preview`).
- Competition/recap slug is **season-prefixed and sometimes renamed** (`2026-dci-tour-preview`,
  sponsor suffixes, prelims/semis/finals variants).
- Bridged by `event_to_competition (event_slug → competition_slug, match_method)`.
- **Because we read the recap link off the list row, we never have to reconstruct this.**

### 1.3 Predictions
- Generated by `sdk/scripts/predictEventRecap.ts` → V9 model → `saveEventPredictionRun`
  (`sdk/src/training/v9EventPredictionDb.ts:142`).
- `model_event_prediction_runs` PK = `prediction_id` = `{event_slug}:{generated_at}`,
  indexed `(event_slug, predicted_at)`. `model_event_prediction_rows` PK =
  `(prediction_id, corps_name)`; carries both `predicted_*` and `actual_*` columns.
- Actuals filled post-event by `updateEventPredictionErrors` (same file, :245).
- **Read path collapses to latest:** `buildCorpsSeasonScores` selects `MAX(predicted_at)`
  per event; the read-model freezes that into `rm_event_prediction` / corps summary JSON.
- **Chart:** `app/components/corps-score-chart.tsx` consumes `CorpsSeasonPoint[]`
  (one point/event: `predicted`, `actual`, `low`, `high`). No snapshot axis, no slider.

### 1.4 Testing baseline
- Vitest via vite-plus (`vite.config.ts`), plus standalone `tsx` assertion scripts in `sdk/test/`.
- HTML **fixtures** in `sdk/test/fixtures/` (real 2024/2025 recap + list pages). No MSW/nock;
  parsers are pure functions over HTML strings.
- DB tests use in-memory libsql (`:memory:`) or a live `dci-relational.db`.

## 2. Target architecture

```
                    ┌─────────────────────────────────────────────┐
   DCI event page → │ scheduled_end (published by DCI, parsed)     │
                    └───────────────┬─────────────────────────────┘
                                    │ at/after scheduled_end
                                    ▼
   /scores/?season=2026  ──►  WATCH: diff list vs ingested ──► new row?
        (poll window)                                   │ yes
                                                        ▼
                              follow row's recap href ──► scrape ──► parse
                                                        │
                                                        ▼
                        ingestWebsiteRecap → corps_scores / category / caption
                                                        │
                                                        ▼
                        updateEventPredictionErrors (fill actuals on past runs)
                                                        │
                                                        ▼
                        FUTURE-ONLY snapshot recalc (shared predicted_at)
                                                        │
                                                        ▼
                        read-model: full snapshot matrix per corps
                                                        │
                                                        ▼
                        corps page chart + "prediction as of ___" slider
```

**Snapshot semantics (the heart of the plan).** A snapshot is identified by
`(season, predicted_at)`. A recalc:
1. Picks `snapshotAt = now` (one value reused for every event in the run).
2. Enumerates events that are **not yet completed** (no ingested result / `start_date > snapshotAt`).
3. Writes one run per future event, all sharing `predicted_at = snapshotAt`.
4. Touches **no** past run.

Rendering "as of *d*": for each event choose `argmax(predicted_at) where predicted_at ≤ d`;
overlay `actual` whenever present. The default view uses `d = latest snapshot` and therefore
already shows the full frozen history of past events plus the newest forecast for future ones.

## 3. Milestones

> Suggested execution order optimizes for **ingest-ready before June 26** first, then history/UI, then automation.

### M0 — Mockable DCI (foundation) — *target: day 1*
- Audit the fetch seam (`sdk/src/config.ts`, `websiteApi.ts`, `websiteScraper.ts`); ensure a
  single injectable `fetchPage(url)` (add one if absent — do not scatter `fetch`).
- Build `sdk/test/support/mockDci.ts`: URL → fixture map with controllable status
  (200 / 404 / empty / slow / changed-between-calls).
- Author synthetic 2026 fixtures under `sdk/test/fixtures/2026/`:
  (a) empty score list, (b) partial list, (c) list with event-name ≠ recap-slug,
  (d) one completed recap, (e) list that grows between two polls (for delta tests),
  (f) a row with a malformed/missing recap link (fallback test).

### M1 — Watch-the-list poller + ingest hardening — *target: days 2–3*
- Implement `watchScoreList(season)`: fetch list → diff against ingested recap slugs
  (reuse `collectScoreListEntries` dedupe) → for each new row, follow `href` → scrape → ingest.
- **No-scores path:** empty/again-empty list → report "no scores yet," write nothing,
  never fabricate a `competitions` row.
- **Unmapped event path:** ingest succeeds via the recap link even when the row's event name
  matches no `events.slug`; record `event_to_competition` heuristically or leave unmapped-but-ingested.
- **Fallback only:** `resolveRecapSlugCandidates(eventSlug, season)` (probe `{season}-{slug}`,
  sponsor strip/add, round expansion, abbreviation map) used **only** when a row's recap link
  is missing/broken.

### M2 — Event-end-driven scheduler — *target: days 3–4*
- Capture `events.scheduled_end` (DCI publishes both start and end times on the event page — parse the
  real end time; fall back to `start + 4h` only if a given event's end is missing/unparseable).
- Scheduler opens a poll window at `scheduled_end`: poll the list every N min for up to M hours
  until the row appears; on success ingest + recalc; on timeout emit an alert. Back off otherwise.
- Decide runtime home (cron script vs. existing job runner — see Open Questions).

### M3 — Versioned predictions (snapshots) — *target: days 4–6*
- Add `snapshotAt` plumbing to `predictEventRecap.ts` season recalc: one shared timestamp;
  enumerate **future events only**; never overwrite past runs.
- Optional `model_prediction_snapshots(snapshot_at, season, label, reason, created_at)` for
  human-friendly slider labels ("as of Jun 27").
- Rewrite the read path: replace `MAX(predicted_at) GROUP BY event_slug` with a snapshot-aware
  build emitting the **full matrix**:
  ```ts
  type CorpsSeasonHistory = {
    snapshots: string[];                 // sorted as-of dates → slider stops
    points: Array<{
      event_slug: string; date: string; label: string;
      actual: number | null;
      byAsOf: Record<string /*snapshot*/, { predicted: number; low: number; high: number }>;
    }>;
  };
  ```
- Update `readModel/builders/corps.ts` + `rm_event_prediction` projection accordingly;
  keep the legacy `CorpsSeasonPoint[]` derivable (latest snapshot) for back-compat.

### M4 — "Prediction as of ___" slider UI — *target: days 6–7*
- Add a slider above `corps-score-chart.tsx`; default = latest snapshot. Sliding recomputes
  the predicted/low/high line client-side from `byAsOf` (pick latest key ≤ selected); actuals fixed.
- A11y + empty/edge states (single snapshot → hide slider; pre-season → forecast only).

### M5 — Robust integration tests — *runs alongside M1–M4*
See §5.

## 4. Success criteria

**Ingest (M0–M2)**
- A new row in the 2026 list fixture is detected and fully ingested (`corps_scores`,
  `category_scores`, `caption_scores`, judges) by following its link — **no slug constructed**.
- Re-running against an unchanged list is a **no-op** (zero duplicate rows).
- An empty list yields a clean "no scores yet" report and **zero writes**.
- Event-name ≠ recap-slug case ingests correctly; `event_to_competition` records the mapping.
- A malformed/missing recap link triggers the candidate-probe fallback and still ingests.
- Scheduler starts watching at `scheduled_end` and stops on first success or timeout-with-alert.

**Predictions / history (M3–M4)**
- Two recalcs at T1 then T2 (after an event completes) produce **two snapshots**; the T1 event's
  T1 run is **byte-for-byte unchanged**, its actuals are filled, and the T2 recalc wrote runs for
  **future events only**.
- `buildCorpsSeasonScores`-equivalent query, given as-of T1, reproduces exactly what we believed
  at T1; given latest, shows frozen past + newest forecast.
- The slider exposes every snapshot date and switching them changes only the predicted line.

**General**
- All new tests run offline against the mock (no network) and pass in CI (`npm run test`).
- No regression in existing `sdk/test/` suite or current corps-page rendering.

## 6. Assumptions

- DCI's 2026 scores list keeps the same DOM shape the current parser targets (`.score-container .tbl-row`,
  recap `href` in the row). **Risk:** DCI redesigns mid-season — mitigated by a fixture refresh + a
  parser that fails loudly rather than silently producing empty results.
- Each list row links to its recap; the recap page is the authoritative score source.
- The V9 model + feature builders remain leak-free "as of" (already designed that way in
  `mlService.buildFeaturesForCorps`), so re-storing past events is unnecessary and we can freeze them.
- The relational DB is single-writer (the pipeline), so snapshot writes don't race.
- DCI publishes both start and end times on event pages (confirmed), so the poll window can key off a
  real `scheduled_end` rather than an estimate.
- "Completed" is determinable per event from ingested results and/or `start_date < now`.
- Read-model is rebuilt after each recalc (existing batch step) — the slider matrix ships pre-baked.

## 7. Open questions

1. **Scheduler runtime home** — standalone cron script, the existing job/queue runner, or a hosted
   scheduled task? Affects M2 packaging and alerting.
2. **Snapshot retention** — keep every snapshot forever (cheap; rows are small) or prune to a curated
   cadence (e.g., one per show night) for a tidy slider? Recommend: keep all, curate the slider's
   exposed stops in the read-model.
3. **`scheduled_end` parsing** — DCI publishes both start and end times (confirmed); remaining question
   is timezone handling (event-local vs. UTC) and how reliably the end time is present across all event
   types (full shows vs. preview/showcase). `start + 4h` stays only as a last-resort fallback.
4. **Poll window params** — interval N and timeout M (e.g., every 5 min for 6 h?), and back-off after
   timeout. Tune against the first few real shows.
5. **Mid-window partial scores** — DCI occasionally posts prelims then finals separately; do we treat
   each new row independently (yes, by dedupe) and recalc after each?
6. **Snapshot trigger policy** — recalc after *every* ingested recap, or batch nightly? (Leaning:
   after each show night, since that's when the forecast meaningfully moves.)
7. **Slider label format** — snapshot date only ("Jun 27") vs. "after {last event}". Needs the
   optional `model_prediction_snapshots.label`.

## 8. Considerations & risks

- **Silent-empty failure mode** is the biggest 2026 risk: a DOM change makes the parser return zero
  rows, which looks identical to "no scores yet." Mitigate: a sanity check (if events are scheduled to
  have ended but list is still empty past a threshold → alert), and parser assertions that flag an
  unexpectedly empty/garbage table.
- **Idempotency** is load-bearing: ingest and recalc must be safe to re-run. Ingest dedupes by recap
  slug; recalc must guard against double-writing a snapshot for the same `(season, predicted_at)` — use
  a stable `snapshotAt` per run and `INSERT OR REPLACE` semantics intentionally.
- **Read-model size** — the snapshot matrix multiplies prediction rows by #snapshots. Still tiny
  (hundreds of events × a handful of snapshots), but cap exposed slider stops if it ever balloons.
- **Back-compat** — keep `CorpsSeasonPoint[]` derivable so nothing downstream breaks during M3/M4.
- **Time handling in tests** — scripts avoid `Date.now()` in some contexts; inject `snapshotAt`/`now`
  so two-snapshot tests are deterministic.
- **Don't fabricate competitions** on empty/partial reads — a half-parsed list must not create
  orphan `competitions`/`corps_scores`.
- **Live-night option (future):** the existing Fate SSE channel (see READ_MODEL_PLAN §0) is the natural
  path for pushing live score updates to open corps pages on competition nights — out of scope here,
  noted for continuity.

## 10. Out of scope

- Live in-arena score streaming / SSE push (future; Fate channel).
- Model retraining or feature changes — this plan only changes *when/how* predictions are stored,
  not how they're computed.
- Backfilling historical snapshots for past seasons (we have only "latest" historically; new history
  accrues from 2026 forward).
